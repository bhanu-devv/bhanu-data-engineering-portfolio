# Bhanudeepak Nagumothu — Portfolio

A Data Engineer portfolio built with Next.js (App Router), TypeScript, Tailwind CSS,
and Zod — and a reusable template for anyone who wants the same architecture with
their own content.

**Live Portfolio:** <https://bhanu-data-engineering-portfolio.vercel.app>

> Rules and plan: [CLAUDE.md](CLAUDE.md) (permanent rules), [PLANNING.md](PLANNING.md)
> (design system, architecture, and phase-by-phase decision log).

## Overview

This is a single-page portfolio for Bhanudeepak "Bhanu" Nagumothu, a Data Engineer.
Every fact on the site traces back to one approved resume — nothing is invented, and
anything not yet supplied (a certification ID, a project link, a recommendation) is
cleanly omitted rather than shown as a placeholder. The codebase is deliberately split
into two halves: **presentation** (`src/`, reusable, has no idea who "Bhanu" is) and
**content** (`content/`, everything personal), so the same site can be re-skinned for
a different person by editing data, not code.

## Design concept: "The Web Is the Pipeline"

Spider-web geometry *is* graph/network/pipeline geometry — nodes joined by strands
that carry things. The site treats that literally: in the hero, strands connect real
technologies from the resume; in the skills section they group into a constellation;
in project modals they become the architecture diagram. The palette is ~92%
grayscale with deep crimson reserved for the single "active" or "live" element in any
one view — never a dominant color.

The influence stays abstract, sophisticated, and cinematic on purpose: no Marvel or
Spider-Man logos, wordmarks, character art, or fan-site aesthetics anywhere in the
code, copy, or assets. All web/network geometry is generated by original code
(`src/components/web/generate-web.ts`), not imported vector art.

## Technology stack

- **Next.js 16** (App Router, Turbopack, Server Components by default)
- **TypeScript** in strict mode
- **Tailwind CSS 4** (CSS-first `@theme` tokens) plus hand-written CSS for bespoke
  depth/motion effects that utility classes can't express cleanly
- **Zod** — the single source of truth for content shape; TypeScript types are
  inferred from the schemas, never hand-duplicated
- **next/font** (self-hosted Space Grotesk, Inter, JetBrains Mono — no external font
  requests) and **next/image** (AVIF/WebP delivery, no layout shift)
- **`tsx`** as a devDependency, to run the path-alias-aware validation scripts

No animation library, no component library, no icon pack: motion is plain CSS
transitions/`@keyframes` plus a few small hooks, and the handful of interactive
pieces (the project dialog, the mobile menu) are built on native `<dialog>` and plain
DOM APIs rather than an added dependency. See CLAUDE.md §7 for the full "why."

## Architecture overview

- **Content-driven, self-hiding sections.** `src/app/page.tsx` renders twelve
  sections in a locked order (`content/navigation.ts`). A section with no
  renderable content — most visibly `Recommendations` before any testimonial is
  approved — returns `null` and disappears from the page, the nav, and structured
  data, with zero code changes needed once real content arrives.
- **One content gateway.** Every section reads content through `@/lib/content` and
  the typed selectors in `src/lib/content-selectors.ts` (e.g. "only approved
  recommendations," "only public social links") — never by importing a raw content
  array and filtering it inline. ESLint enforces the import boundary.
- **Schema-first types.** `src/schemas/content.ts` defines every content shape once,
  as a Zod schema; `src/types/content.ts` infers TypeScript types from it. A field
  that isn't known yet is `needsInput("reason")`, not a placeholder string.
- **Server Components by default.** `"use client"` is used only where real
  interaction lives — the project dialog, the mobile navigation menu, pointer-tilt —
  and pushed as far down the component tree as possible.
- **One resume source.** `content/resume.ts` plus `src/lib/resume.ts` are the only
  place the resume's path, filename, and metadata are defined; every "View" and
  "Download" action reads the same helper.

## Folder structure

```
content/            All personal content (typed TS modules) — edit this to customize
content.example/    A complete, fictional mirror of content/ for template users
public/              Images and the resume PDF
scripts/             content-check.ts and resume-check.ts (run via tsx)
src/
  app/               Routes, layout, metadata, global styles
  components/
    layout/          Header, Navigation, Footer
    sections/        One component per page section (Hero, About, Projects, ...)
    seo/             Structured-data (JSON-LD) components
    ui/              Presentation-agnostic primitives (Button, Surface, SectionShell, ...)
    web/              The web/network geometry system (generator + renderers)
  hooks/             Small reusable client hooks (reduced-motion, tilt, active-section, ...)
  lib/               The content gateway, selectors, the resume helper, UI strings
  schemas/           Zod schemas — the single source of content shape
  styles/            Design tokens, depth/surface system, web-geometry CSS
  types/             TypeScript types, inferred from the schemas
```

## Content-driven architecture

Nothing personal — no name, number, date, or link — lives inside a component.
`content/` holds it all as typed modules (`site.ts`, `experience.ts`, `projects.ts`,
...), validated by `src/schemas/content.ts`. Run:

```bash
npm run content:check
```

This checks shape (via Zod) plus a set of safety/privacy rules a type alone can't
express: no phone-number-like value anywhere except the one approved field, no
`reference/`-only material, no secrets or obvious placeholder text ("TBD", "lorem
ipsum", ...), no unapproved recommendation, and more. It reports **errors** (must be
fixed) and **informational notes** (expected, currently-open gaps, like an unpicked
domain) separately.

## Customizing content (using this as a template)

**`content.example/`** is a complete, structurally valid, entirely fictional mirror
of `content/` — a made-up person ("Jordan A. Rivera") at fictional companies,
demonstrating every optional pattern the schema supports. To start your own site:

1. Copy the shape of each `content.example/*.ts` file into the matching
   `content/*.ts` file.
2. Replace the fictional data with your own facts. Leave anything you don't have yet
   as `needsInput("reason")` — it will be validated and cleanly omitted, never shown
   as a placeholder.
3. Validate: `npm run content:check -- --example` runs the identical rule set
   against the example content, so you can see the mechanism before touching your
   own data.

### Replacing the portrait

The portrait is rendered from `content/site.ts`'s `portrait` field (path, alt text,
and dimensions) through `next/image`, with the grayscale/dimensional-frame treatment
applied entirely in CSS at render time — the source file itself is never edited.
Replace the file at that path with your own square portrait and update the `alt`
text; no component changes are needed.

### Replacing the resume

The resume has one stable public path, `/resume/bhanu-resume.pdf`, set once in
`content/resume.ts`. To update it:

1. Export the new PDF.
2. Overwrite `public/resume/bhanu-resume.pdf` (same filename — never add a version
   or date to it).
3. Run `npm run resume:check` — confirms it's a real PDF at the right path, and that
   nothing in the codebase hardcodes a second resume path.
4. Commit.

No component or config edit is needed. Every "View Resume" / "Download Resume"
action reads the same `content/resume.ts` config through `src/lib/resume.ts`, which
also appends a content-hash query string so browsers never serve a stale cached copy
after a replacement.

## Development

```bash
npm install
npm run dev
```

Open <http://localhost:3000>.

| Command | Purpose |
|---|---|
| `npm run dev` | Development server |
| `npm run build` | Production build |
| `npm run start` | Serve the production build locally |
| `npm run lint` | ESLint, including the import-boundary rules |
| `npm run typecheck` | Generates route types, then runs `tsc --noEmit` |
| `npm run content:check` | Validates `/content` — shape, plus privacy/safety rules |
| `npm run content:check -- --example` | Validates `content.example/` with the same rules |
| `npm run resume:check` | Verifies the resume PDF exists, is a real PDF, and is at the single locked path |

Before a change is considered done, all six of the above should pass.

## Privacy model

- **Public by design:** the professional email, phone number, LinkedIn, and GitHub
  profile links that appear on this site are all explicitly approved for public
  display by their owner. The phone number is deliberately rendered in exactly one
  place — the Contact section, as a `tel:` link — and never in navigation, the
  footer, page metadata, Open Graph data, or structured data; `content:check` scans
  for phone-number-shaped values anywhere else and fails the build if it finds one.
- **Nothing invented:** job titles, dates, metrics, technologies, certifications,
  degrees, awards, and project outcomes all trace back to one approved resume.
  Anything not yet supplied is validated as an open item and omitted from the
  rendered site — never a placeholder, a guessed ID, or an invented link.
- **Project visuals are sanitized by policy:** every architecture diagram is a
  custom SVG/React diagram built from already-public resume facts — never a
  screenshot or export of a real system, and never a real table, schema, server, or
  vendor name.
- **`reference/`** (this author's original source material and a separate reference
  portfolio used only for layout inspiration) is gitignored and was never committed,
  at any point in this repository's history.

## Reusable template

This repository is meant to be forked. The reuse mechanism is the content/
presentation split described above: a fork changes `/content` and `/public` and
gets a working, personalized site with the same design system, validation, and
accessibility/performance baseline. See [CONTENT-NOTICE.md](CONTENT-NOTICE.md) for
exactly what is and isn't reusable.

## Deployment

The app is built to be static-export compatible: no API routes and no server-only
runtime features, so it can deploy to Vercel, Netlify, Cloudflare Pages, or GitHub
Pages without modification. This site is deployed on Vercel at
<https://bhanu-data-engineering-portfolio.vercel.app> (no custom domain yet).

The canonical site URL is set once, as `site.seo.url` in `content/site.ts`; the
canonical link, `metadataBase`, Open Graph/Twitter URLs, JSON-LD, `robots.txt`, and
`sitemap.xml` all derive from it. A fork deploying elsewhere changes that one value
(or leaves it as `needsInput()`, in which case every absolute-URL field is omitted).
